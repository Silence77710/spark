# 技术架构

> Spark 是 S1 工具型全栈应用：前端 Next.js（App Router）+ 后端 Next.js API 路由 + 本机 MySQL + 可选 AI 思考伙伴。本文件描述实际代码所揭示的技术架构，作为新成员上手与外部评审的权威来源。
>
> 业务视角见 [业务.md](./业务.md)；接口契约见 [接口.md](./接口.md)；数据模型见 [数据模型.md](./数据模型.md)；部署流程见 [部署.md](./部署.md)。

## 二、分层结构

```
┌──────────────────────────────────────────────────────────┐
│  apps/web（Next.js App Router，单进程）                   │
│  ┌──────────────────────┬──────────────────────────────┐ │
│  │  src/app/（页面）    │ / · /explore · /graph · ... │ │
│  │                      │ /ideas/[id] · /settings      │ │
│  ├──────────────────────┼──────────────────────────────┤ │
│  │  src/app/api/（路由）│ /api/ideas · /api/ai/*       │ │
│  │                      │ /api/settings · /api/...     │ │
│  ├──────────────────────┴──────────────────────────────┤ │
│  │  src/components/（展示单元）                  │ │
│  │  src/hooks/（可复用客户端 hooks）              │ │
│  │  src/lib/（配置、纯函数、类型）                │ │
│  └──────────────────────────────────────────────┘ │
└──────────────────────┬───────────────────────────────┘
                       │ import
                       ▼
┌──────────────────────────────────────────────────────────┐
│  packages/@spark/（共享包，workspace 内 import）         │
│  ┌──────────┬──────────┬──────────┬──────────┐           │
│  │ @spark/  │ @spark/  │ @spark/  │ @spark/  │           │
│  │    ai    │    db    │   utils  │    ui    │           │
│  │12 模块   │连接池    │重要性等  │预留      │           │
│  └──────────┴──────────┴──────────┴──────────┘           │
└──────────────────────┬───────────────────────────────┘
                       │ TCP 3306
                       ▼
              ┌────────────────────┐
              │ MySQL 8 容器       │
              │ spark-mysql        │
              │ 库 `spark`         │
              └────────────────────┘
```

**核心约束**：

1. 单进程：Next.js 同时承载 SSR 渲染和后端 API，不分离前后端进程。
2. 共享代码靠 workspace 包，不复制副本（AGENTS.md「共享配置唯一定义」硬规则）。
3. 数据只走 MySQL，无独立缓存层（V1 阶段）；AI 调用串行排队，不并发打上游。

### 3.2 页面组件分层

```
src/app/<page>/page.tsx          # 页面入口：状态编排 + 组合（≤ 400 行）
        │
        ▼
src/components/<domain>/...      # 展示单元，按功能点拆分（AGENTS.md 硬规则）
        │
        ▼
src/lib/config.ts                # 共享配置唯一定义
src/lib/types.ts                 # 领域类型
src/lib/<helper>.ts              # 纯函数
        │
        ▼
src/hooks/                       # 客户端 hooks（use-ai-companion 等）
```

页面只做编排（取数据 → 组合组件 → 渲染），不在页面内写大段展示逻辑或业务计算。

### 3.3 API 路由风格

- 全部使用 Next.js Route Handlers（`route.ts` 导出 `GET/POST/PATCH/DELETE`）。
- 入参：URL 参数 + JSON body；出参：JSON。
- 错误：HTTP 状态码 + `{ error: string }` 主体（详见 [接口.md](./接口.md)「通用约定」）。
- 不直接持有事务；如需多步写入，按顺序串行调用 `query()`，依赖依赖关系由 schema FK 保障。

## 四、共享包（packages/@spark）

### 4.1 `@spark/ai`（AI 调用层）

入口：`packages/@spark/ai/src/index.ts`。

| 模块 | 作用 |
|------|------|
| `provider` | OpenAI 兼容 chat completion 客户端，含串行队列与 429/5xx 重试 |
| `socratic` | 苏格拉底提问 |
| `connector` | 想法之间的隐式关联发现 |
| `catalyst` | 跨想法催化剂配对 |
| `retro` | 复盘对话（多轮） |
| `mirror` | 镜像洞察（个人模式） |
| `devil` | 魔鬼代言人（反向论证） |
| `coroner` | 想法死因复盘 |
| `translator` | 跨领域翻译 |
| `blindspot` | 盲点检测 |
| `profile` | 思考画像生成 |
| `analyzer` | 多维度分析（V1 新增） |

调用模型：所有 AI 模块最终都走 `provider.chatCompletion()`，由该函数统一：

- 加载 `AI_API_KEY` / `AI_BASE_URL` / `AI_MODEL`（缺 `AI_API_KEY` 抛错，AI 功能静默降级）；
- 进入 `globalThis.__sparkAiQueue` 串行队列，规避上游 429；
- 对 429/5xx/网络错误最多重试 2 次；
- 不写持久层：调用方负责把结果写入 `idea_activities` 或专用表。

**这是为什么多个 AI 功能同时触发时后发的请求会排队等待——属正常现象。**

### 4.2 `@spark/db`（数据层）

入口：`packages/@spark/db/src/index.ts`。

- 导出 `getPool()`：懒加载 mysql2 连接池，单例；
- 环境变量：`MYSQL_HOST` / `MYSQL_PORT` / `MYSQL_USER` / `MYSQL_PASSWORD` / `MYSQL_DATABASE`，默认 `127.0.0.1:3306` / `root` / `spark123` / `spark`；
- `query<T>()` 包装 `pool.execute()`，统一参数化查询；
- 表结构脚本：`packages/@spark/db/schema.sql`（详见 §五）。

依赖：`mysql2`（生产）；`better-sqlite3` 也列在依赖中但未使用——保留是为后续内嵌场景预留，不在 V1 范围。

### 4.3 `@spark/utils`（纯函数工具）

`importance.ts` 提供想法重要程度计算（与 [业务.md](./业务.md)「重要程度」章节一致）。无副作用、可在客户端直接调用。

### 4.4 `@spark/ui`（UI 共享组件）

当前为空包，结构预留。V1 阶段展示单元直接放在 `apps/web/src/components/`，跨项目复用场景出现时再启用此包。

## 五、数据架构

### 5.1 表清单（V1 已建）

`packages/@spark/db/schema.sql` 包含 3 张核心表（详细字段见 [数据模型.md](./数据模型.md)）：

| 表名 | 作用 | V1 状态 |
|------|------|--------|
| `ideas` | 想法主表（含状态、血缘、情绪、解锁时间等扩展字段） | 已建 |
| `idea_activities` | 想法活动时间线（含 AI 调用结果持久化） | 已建 |
| `settings` | 键值对设置（自定义重要性名称等） | 已建 |

V1 文档（[接口.md](./接口.md) / [数据模型.md](./数据模型.md)）按完整产品形态描述了 7 张表，但实际 schema 只实现了核心三张——其余表（`collections` / `idea_relationships` / `analysis_runs` / `thinking_profiles`）会在 V1.1/V1.2 渐进引入，**接口契约已先行登记，实现需在文档同步原则下补齐**。

### 5.2 表关系

```
ideas (1) ──< idea_activities (N)
   │
   └── 自引用：parent_a_id / parent_b_id → ideas.id（血缘/合并关系）
```

`idea_activities.idea_id` 是带 `ON DELETE CASCADE` 的 FK；血缘字段不带 FK（允许松散引用）。

### 5.3 索引

当前显式建索引：

- `idx_idea_activities_idea_id`（按想法查询活动）
- `PRIMARY KEY (id)` / `UNIQUE` 由 MySQL 自动维护

其他查询热点（按 status、collection、时间范围）依赖 InnoDB 的聚簇索引与全表扫描，V1 阶段数据量小不构成瓶颈。

### 5.4 迁移

V1 阶段无版本化迁移工具（Flyway/Liquibase 未引入）。变更流程：

1. 编辑 `packages/@spark/db/schema.sql`；
2. 同步追加 `docs/数据模型.md`；
3. 在 `docs/变更日志.md` 标注 `feat(db)`；
4. 本地执行 `docker exec -i spark-mysql mysql -uroot -pspark123 < packages/@spark/db/schema.sql`（CREATE TABLE IF NOT EXISTS 保证幂等）；
6. 生产回滚策略见 [部署.md](./部署.md)「回滚」章节。

## 六、AI 集成架构

### 6.1 调用链

```
浏览器（想法详情页）
  │
  │ POST /api/ai/<module>
  ▼
Next.js Route Handler（apps/web/src/app/api/ai/）
  │
  │ 调对应模块函数（如 analyzer.analyzeIdea）
  ▼
packages/@spark/ai/src/<module>.ts
  │
  │ 经 provider.chatCompletion()
  ▼
globalThis.__sparkAiQueue（串行队列）
  │
  │ 单飞
  ▼
HTTP POST <AI_BASE_URL>/chat/completions
  │
  ▼
OpenAI 兼容上游（默认 tokens.store / deepseek-v4-flash）
```

### 6.2 串行队列实现要点

- 队列挂在 `globalThis.__sparkAiQueue`（Next.js 多个 route 模块独立打包，需跨实例共享）；
- `enqueue(fn)` 把新任务链到上一次的 `then`，新任务失败不影响队列后续执行（`.catch(() => {})` 兜底）；
- 429/5xx/网络错误最多重试 2 次（指数退避可选，V1 固定 1s × 2）；
- 不做请求合并、token 缓存、prompt 优化——V1 阶段保持简单。

### 6.3 降级行为

- `AI_API_KEY` 缺失：抛 `Error("AI_API_KEY 未配置...")`，前端拿到 500 + 友好提示，其他功能不受影响；
- 上游 429 多次重试仍失败：返回 502 + 提示用户稍后重试；
- AI 结果持久化：调用方负责把 JSON 解析后的结果写入 `idea_activities.content` 或专用分析表。

## 七、构建与运行架构

### 7.1 开发模式

```bash
pnpm install
pnpm dev      # → cd apps/web && next dev（端口 3000）
```

- 单进程同时跑 SSR 和 API；
- 文件变更触发热更新；
- 数据库在本机 `spark-mysql` 容器中独立运行（不在 dev 进程内）。

### 7.2 生产模式

```bash
pnpm build    # → cd apps/web && next build
pnpm start    # → cd apps/web && next start
```

或 Docker（详见 [部署.md](./部署.md)）：

```bash
docker build -t spark-web:local .
docker run -d --name spark-web -p 3000:3000 \
  -e MYSQL_HOST=host.docker.internal \
  -e AI_API_KEY=... \
  spark-web:local
```

- 单容器单进程：Next.js standalone 输出 + node 启动；
- 容器通过 `host.docker.internal` 访问宿主 MySQL；
- AI 调用走 `AI_BASE_URL`（默认中转 URL）。

### 7.3 进程拓扑

```
┌─────────────────────┐
│  反向代理（nginx）   │  :80 / :443
└──────────┬──────────┘
           │ proxy_pass
           ▼
┌─────────────────────┐
│  Next.js 容器        │  :3000
│  spark-web          │
│  (单进程)           │
└──────────┬──────────┘
           │ mysql2 over TCP
           ▼
┌─────────────────────┐
│  MySQL 容器          │  :3306
│  spark-mysql        │
└─────────────────────┘
```

外部依赖：AI 上游（出站 HTTPS）。无 Redis / 消息队列 / 外部对象存储。

## 八、安全与运维

### 8.1 密钥与配置

- `.env.local` 不入库（仓库根 `.gitignore`）；
- `AI_API_KEY` / `MYSQL_*` 经运行时环境变量注入；
- 仅 `apps/web/.env.local` 用于本地开发，模板在根 `.env.example`；
- AI key 缺失时不静默用兜底值——必须显式配置（fail loud）。

### 8.2 网络边界

- MySQL 容器与 web 容器在 Docker 默认 bridge 网络；
- 反向代理仅暴露 80/443，3306 不对外；
- AI 上游走 HTTPS 出站，不暴露端口。

### 8.3 错误处理

- API 路由：4xx 给业务错误（含 `error` 文案），5xx 给通用提示，不泄露栈；
- 前端：每个 AI 面板有自己的失败态，按钮可重试；
- 日志：Next.js 默认 `console`，生产由容器 stdout 收集。

### 8.4 备份策略

- MySQL 容器 `spark-mysql` 数据卷挂载到宿主，**手动 `mysqldump` 备份**（V1 阶段未引入自动备份脚本）；
- 上线检查清单见 [部署.md](./部署.md)「上线检查」。

## 九、性能与可扩展性

### 9.1 当前瓶颈（V1）

- AI 调用：上游限流（429）+ 串行队列，是 AI 功能的天然瓶颈；
- MySQL：单实例，无读写分离；
- Next.js：单进程，单实例部署；并发受 Node 事件循环与单核 CPU 限制。

### 9.2 V1 不引入

- 多实例部署 / PM2 cluster / K8s；
- Redis 缓存层；
- 全文检索（ES/Meilisearch）；
- 异步任务队列（BullMQ 等）。

### 9.3 V2+ 演进方向（仅作接口预留）

- 多实例部署：AI 串行队列需要替换为 Redis 分布式锁；
- 读多：MySQL 主从 + Prisma/drizzle 切换；
- 复杂检索：引入 ES 索引 `ideas.content`。
