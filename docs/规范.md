# 工程规范

> 本文件是 Spark 项目的工程级 rules 集合，定义代码与文档协同、提交前自检、协作流程的统一规则。
>
> 与根 [AGENTS.md](../AGENTS.md)「文档同步（硬规则）」「代码组织（硬规则）」配套；本文件给出更细的执行细则。

---

## 〇、核心规则（First Rule）

> **任何对代码、业务、接口、数据、部署的改动，必须在同一次变更中同步更新受影响的文档。文档与代码不一致视为缺陷（bug）。**

这一条高于一切。任何"先合并代码，文档回头再补"的行为都视为违规；任何"因为忙就跳过文档"的借口都不成立。

---

## 一、文档同步规则（与 AGENTS.md 硬规则一一对应）

下表是改动触发条件与目标文档的对应关系。任一触发条件命中，必须在同一次提交里更新对应文档。

| 改动类型 | 同步更新的文档 |
|---------|--------------|
| 技术栈、数据存储、目录结构、运行方式变化 | [AGENTS.md](../AGENTS.md) + [架构.md](./架构.md) |
| 功能规格、数据模型、交互行为变化 | [SPEC.md](../SPEC.md) |
| 产品定位、版本范围、设计哲学变化 | [PRODUCT.md](../PRODUCT.md) |
| 接口契约变化（新增/修改/删除端点、参数、响应、错误码） | [接口.md](./接口.md)；必要时同步 [数据模型.md](./数据模型.md) |
| 领域对象、状态机、核心流程变化 | [业务.md](./业务.md) |
| 技术架构变化（依赖、分层、AI 调用链、构建链路） | [架构.md](./架构.md) |
| 部署链路、构建参数、镜像标签、环境变量、迁移脚本变化 | [部署.md](./部署.md) |
| 每次发版或合并到主干的提交 | 追加一行到 [变更日志.md](./变更日志.md) |

执行细则：

1. **同一 PR 内完成**——不允许出现一个 PR 只改代码不改文档的提交。
2. **同一 commit message 内体现**——commit message 中应出现 `docs:` / `docs(api):` / `docs(db):` 等前缀说明本次同步的文档范围。
3. **接口先行**——任何对外暴露的接口，必须先在 [接口.md](./接口.md) 登记契约，再实现代码。
4. **schema 与文档双向同步**——`packages/@spark/db/schema.sql` 的字段变化必须同步 [数据模型.md](./数据模型.md) 的字段表，反之亦然。

## 二、文档清单与责任人

`docs/` 目录按"做什么"分配主题，每篇文档有唯一主题，不重复不重叠。

| 文档 | 主题 | 主更新人 | 更新时机 |
|------|------|---------|---------|
| [概览.md](./概览.md) | 索引、阅读顺序、维护原则 | 项目维护者 | 文档结构变动时 |
| [业务.md](./业务.md) | 领域对象、用户场景、核心流程、状态机 | 产品负责人 | 业务规则、流程变化时 |
| [接口.md](./接口.md) | HTTP API 契约（端点、参数、响应、错误码） | 后端开发 | 接口新增/修改/删除时 |
| [数据模型.md](./数据模型.md) | 表结构、字段、枚举、跨表关系 | 后端开发 | schema 变化时 |
| [架构.md](./架构.md) | 技术栈、分层、AI 集成、构建与运行、依赖图 | 架构/全栈 | 技术架构变化时 |
| [部署.md](./部署.md) | 环境、构建、Docker、迁移、上线、回滚、监控 | 运维/全栈 | 部署链路变化时 |
| [变更日志.md](./变更日志.md) | 版本、变更类型、影响范围、迁移说明 | 每次提交者 | 发版或合入主干时 |
| [规范.md](./规范.md) | 本文件：工程级 rules | 项目维护者 | 规范本身调整时 |

**单一信息源原则**：每条事实只在一处定义；其他文档通过链接引用，禁止复制副本（参见 [AGENTS.md](../AGENTS.md)「共享配置唯一定义」硬规则，文档版本同样适用）。

## 三、提交前自检清单

执行 `git diff --stat` 后，对照下列清单逐项打勾。**任何一项未完成，禁止 commit**。

### 3.1 通用项

- [ ] 本次改动涉及的代码、配置、脚本均已纳入 diff（无遗漏）。
- [ ] 改动行数符合 [AGENTS.md](../AGENTS.md)「单文件长度」硬规则：单文件 ≤ 400 行（建议）/ ≤ 600 行（强制）。
- [ ] 没有引入未在 `package.json` 中声明的依赖。
- [ ] 没有修改 `.env` / `.env.local`，仅修改 `.env.example`（如有需要）。

### 3.2 文档同步项

按 §一 表格对照本次 diff：

- [ ] 接口契约变化 → [接口.md](./接口.md) 已更新；必要时 [数据模型.md](./数据模型.md) 已同步。
- [ ] 数据模型变化 → `packages/@spark/db/schema.sql` 与 [数据模型.md](./数据模型.md) 双向一致。
- [ ] 技术架构变化 → [架构.md](./架构.md) 已更新（栈、分层、依赖图任一变化均需）。
- [ ] 部署链路变化 → [部署.md](./部署.md) 已更新（环境变量、镜像、迁移脚本任一变化均需）。
- [ ] 业务流程变化 → [业务.md](./业务.md) 已更新（领域对象、状态机、流程任一变化均需）。
- [ ] 任何合入主干的提交 → [变更日志.md](./变更日志.md) 已追加一行。

### 3.3 代码质量项

- [ ] TS 编译通过（`pnpm typecheck` 或 IDE 0 错误）。
- [ ] 没有遗留 `console.log` / 调试代码（生产代码）。
- [ ] 错误处理覆盖：API 路由给出 4xx/5xx + 友好提示；前端有错误态。
- [ ] 涉及 AI 调用：未绕开串行队列直接打上游。

### 3.4 上线前额外项

合并到主干并准备发版时：

- [ ] [变更日志.md](./变更日志.md) 顶部已标注版本号与日期。
- [ ] [部署.md](./部署.md)「上线检查」章节逐项完成。
- [ ] 已告知团队本次变更的迁移说明（如有破坏性变更）。

## 四、协作流程

### 4.1 一次典型的特性合并

```
1. 接到需求，参考 [业务.md](./业务.md) 与 [SPEC.md](../SPEC.md) 确认范围。
2. 若涉及新接口，先在 [接口.md](./接口.md) 起草契约。
3. 编码实现。
4. 同步更新所有触发的文档（按 §一）。
5. 执行 §三 自检清单。
6. 写 commit message（参考 PSES writing-commit-messages skill）。
7. 提交 PR；PR 描述中列出"文档变更"清单。
8. 合入主干后追加 [变更日志.md](./变更日志.md) 一行。
```

### 4.2 冲突处理

- 文档与代码不一致：默认以**代码为准**是错的——文档与代码必须双向同步，无单方权威。
- 接口契约变更未通知调用方：视为破坏性变更，必须先升 minor/major 版本。
- 迁移脚本回滚失败：参考 [部署.md](./部署.md)「回滚」章节，必要时直接恢复容器到上一个 tag。

### 4.3 与外部参考项目的关系

本项目的工程级规范参考 [PSES](../personal-engineering-standard/)。与同级项目（[frontend-scaffold](../frontend-scaffold/) / [service-scaffold](../service-scaffold/)）的关系：

- 共享目录结构模式（apps/ + packages/）；
- 不直接复制代码——每个项目有自己的 AGENTS.md / SPEC.md / docs/；
- 新成员交叉参考：先读本仓库的 AGENTS.md / docs/，再去同级项目看对照实现。

## 五、违反后果

文档同步是协作底线，违反后果与代码缺陷等同：

| 等级 | 行为 | 后果 |
|------|------|------|
| L1 | 单次遗漏文档同步，但未引起线上问题 | 退回 PR，要求补齐后重提 |
| L2 | 文档陈旧导致他人接入报错 | 立即修复；下次评审重点关注文档 |
| L3 | 接口契约与实现长期不一致，导致外部调用方失败 | 视为事故；记录到 [变更日志.md](./变更日志.md)；启动复盘 |

协作不是个人英雄主义——文档同步是降低团队认知负担的工具，不是负担本身。

---

## 六、变更记录

本文档（rules 本身）的变更需满足：

1. 任何规则的增删改必须在 PR 描述中明确说明；
2. 重大规则变更（例如新增硬规则）需在 [变更日志.md](./变更日志.md) 标注 `docs(rules)`；
3. 规则生效后，所有现存 PR 按新规则自检。
